# CLAUDE.md

Site estático da **Gringos Washboard Band** (gringoswashboard.com), por agora publicado no **GitHub Pages** a partir de `dist/` (`https://rdquintas.github.io/gringoswashboard.com/dist/`); o `netlify.toml` fica preparado para mais tarde. O `README.md` tem a documentação completa; este ficheiro é o resumo para trabalhar no código.

Idioma do projeto: **português (pt-PT)** — código, comentários, mensagens do build e commits. O site é bilingue: português (`lang="pt-PT"`, na raiz) e inglês (`lang="en"`, em `en/`) — ver **Línguas**; nomes de canções, álbuns e publicações ficam no original.

## Estado atual

Site de uma página (`index.html`) com secções (hero, agenda, live session, música, a banda, footer com newsletter), a página de imprensa (`press.html`), o EPK (`epk.html`, Electronic Press Kit: apresentação, trajetória, Root of the Oppressed, vídeo, especificações técnicas) e duas páginas legais (`privacidade.html`, `politica-cookies.html`). HTML escrito à mão, **sem templates nem framework**; o build copia `src/` → `dist/`, inclui os partials comuns (header/menu e footer) e preenche alguns marcadores a partir de `src/conteudo/home.yaml`. Única dependência: `sharp` (devDependency, conversão de imagens); sem testes nem linter: validar correndo `npm run build`.

Muitas imagens ainda são placeholders de `placehold.co`.

Inspiração para a evolução futura: o repositório [rdquintas/entrelinhasbar.com](https://github.com/rdquintas/entrelinhasbar.com) (build em Node que gera `dist/` a partir de YAML + templates).

## Comandos

```bash
npm run build        # node build.js → gera dist/
npm run dev          # build + npx serve dist (http://localhost:3000/)
```

Node 22 (`.nvmrc`, `netlify.toml`).

## Estrutura

- **`build.js`** — limpa `dist/`, copia `src/` para lá (exceto `conteudo/`, `partials/`, `modelos/` e as páginas), gera cada página (e a de cada concerto da agenda) uma vez por língua (constante `LINGUAS`), inclui os partials, aplica as configurações de `src/conteudo/home.yaml` (parser YAML mínimo próprio: mapas e listas, incluindo listas de mapas `- chave: valor`, aninhados por indentação com espaços, e blocos de texto `|`/`|-`), acrescenta `?v=<hash>` aos links para `css/style.css` e `js/main.js` (cache busting), converte as imagens e gera `sitemap.xml` (um URL por cada `.html` na raiz de `src/` e por cada concerto, em cada língua; `lastmod` = data do ficheiro, ou do `home.yaml` nos concertos) e `robots.txt`. URL base na constante `SITE_URL`.
- **`src/`** — ficheiros do site:
  - `conteudo/home.yaml` — configurações do site, agrupadas por secção: `section_hero` com `hero` (lista do slideshow: cada item com `horizontal` e `vertical`, ficheiros em `images/`) e `duracao_hero` (segundos que cada imagem fica visível); `section_about` com `texto_pt` e `texto_en` (blocos `|-`, em Markdown; ver **Sobre**); `section_agenda` com `gigs` (lista de concertos) e `default_images` (`hero` e `hero_v`, ver **Agenda**); `section_single_video` com `youtube`, `title_pt`/`title_en` e `text_pt`/`text_en` (vídeo em destaque, ver **Vídeos**); `section_media` com `youtube_1` e `youtube_2` (ver **Vídeos**) e `fotos` (lista de ficheiros em `images/`, ver **Fotos**). Entre plicas, `''` é uma plica.
  - `conteudo/epk.yaml` — hero do EPK: `hero_horizontal` e `hero_vertical` (ficheiros em `images/`, PNG ou JPG); o build substitui `<!-- @epk-hero -->` em `epk.html` pelas duas `<img>` (`.hero-h`/`.hero-v`, a vertical só com `orientation: portrait`), com as medidas reais; `image_share` é a imagem de partilha do EPK (convertida como as outras para `dist/images/og/_epk.jpg`; vazia, fica a `default_share_image`). `section_01`, `section_02`, `section_03` e `section_05` (constante `EPK_SECOES`) são as secções `#apresentacao`, `#trajetoria`, `#root-of-the-oppressed` e `#especificacoes`: o build substitui cada `<!-- @epk-section_NN -->` pelo `h2.section-title` com o `title.<língua>` (vazio não é colocado) e pelo `text.<língua>` (bloco `|-`, em Markdown, convertido pelo mesmo `markdown()` do **Sobre**). `section_04` é o vídeo (`#video`): `<!-- @epk-section_04 -->` dá o `h2` com o `title.<língua>` e o `.embed.epk-video` do `youtube` (obrigatório; ID tirado como em **Vídeos**; o título também vai para `data-title`, barra e rótulos).
  - `conteudo/site.yaml` — dados comuns a todas as páginas: `contactos` (o build substitui cada `<!-- @email -->` pelo link `mailto:` de `contactos.email` e cada `<!-- @telefone -->` pelo link `tel:` de `contactos.telefone`; `<!-- @whatsapp -->`, no footer por baixo do telefone, dá o botão `images/whatsapp.png` com link `https://wa.me/<dígitos>` de `contactos.whatsapp`, e se estiver vazio a linha é retirada) e `links` (redes sociais: `facebook`, `instagram`, `youtube`, `spotify`, `soundcloud`, `bandcamp`; as aceites estão na constante `REDES` do `build.js`) e `google_analytics_id` (ID do GA4, `G-…`; ver **Cookies / Google Analytics**). O build substitui cada `<!-- @social -->` dos partials pela `<ul class="social">`, pela ordem do YAML, com `target="_blank" rel="noopener"`; uma rede com link vazio não é colocada (sem nenhuma, a `<ul>` também não).
  - `conteudo/paletas.yaml` — paletas de cores alternativas para experimentar (ver **Paletas**).
  - `partials/` — HTML comum a todas as páginas: `header.html` (do `<!DOCTYPE>` ao `<body>`, com o `<head>` completo, + header + menu fullscreen) e `footer.html` (conteúdo do `<footer>`). O build substitui cada `<!-- @partial nome chave="valor" … -->` pelo `partials/nome.html`, com a indentação do marcador; cada `{{chave}}` do partial leva o valor do atributo (obrigatório; `{{chave?}}` é opcional e um `class=""` vazio é retirado). No header, acrescenta `aria-current="page"` ao link do menu cujo `href` é a própria página.
  - `modelos/evento.html` — modelo da página de cada concerto (ver **Agenda**); não é copiado para `dist/`.
  - `index.html`, `press.html`, `epk.html`, `privacidade.html`, `politica-cookies.html` — páginas que começam por `<!-- @partial header titulo="…" descricao="…" classe="…" -->` (`<title>`, meta description e classe opcional do `<body>`) e têm, dentro do `<footer>`, `<!-- @partial footer -->` (a tag `<footer>` fica na página porque varia: no index tem `section--black` e a curva SVG).
  - `css/style.css` — todos os estilos, organizados por secções (`/* ---------- Hero ---------- */`); cores e fontes como variáveis em `:root`.
  - `js/palette.js` — carrega a paleta de `?palete_id=` (ver **Paletas**).
  - `js/main.js` — JS vanilla sem dependências (IIFE): menu fullscreen, reveal ao fazer scroll, efeitos "tada"/pulse, agenda (tira concertos passados), newsletter (mock), aviso de cookies + Google Analytics, ano no footer. Acrescenta a classe `js` ao `<html>`.
  - `images/` — `hero01–03.png` e `hero01–03_v.png` (slideshow do hero, horizontal 1920×900 e vertical 1080×1920), `band.jpg`.
- **`dist/`** — gerado, mas **versionado** (o GitHub Pages serve-o e não corre build): correr `npm run build` e fazer commit de `dist/` junto com `src/`. O `.nojekyll` na raiz impede o Jekyll do Pages de esconder ficheiros começados por `_` (ex.: `images/og/_default.jpg`).
- **`netlify.toml`** — `npm run build`, publica `dist`, Node 22, cabeçalhos de segurança.

## Convenções

- **Hero:** as imagens e o tempo vêm do `home.yaml`. O build substitui `<!-- @hero-imagens -->` em `index.html` por um `<div class="hero-slide">` por imagem, com as duas `<img>` (`.hero-h` e `.hero-v`, `loading="lazy"`; o CSS mostra a vertical só com `orientation: portrait`) e `/* @hero-animacao */` em `style.css` pela animação dos `.hero-slide` (`@keyframes hero-fade`, ciclo = nº de imagens × `duracao_hero`, `animation-delay` negativos, fade de 1,5s na constante `HERO_FADE`). Crossfade só com CSS. Os botões vêm de `cta1` (dourado) e `cta2` (preto), com texto em `pt`/`en` e `link`: o build substitui `<!-- @hero-cta -->` pelo `<div class="hero-cta">`; um CTA com `link` vazio não é colocado (sem nenhum, o `<div>` também não).
- **Sobre:** o build substitui `<!-- @about -->` (secção `#band` do `index.html`) pelo `section_about.texto_<língua>` do `home.yaml`, convertido por `markdown()` no `build.js` (Markdown mínimo próprio, sem dependências): `##`/`###` (com `.section-title`; `#` dá erro), parágrafos, `> …` (`.pullquote`), listas `- `, imagem sozinha `![alt](ficheiro)` (em `images/`, tem de existir), `::: split` … `:::` (`.about-split`: texto seguido numa `div.reveal`, cada imagem numa coluna; imagem primeiro → `.about-split--left`), `{.classe}` no fim de um bloco e blocos HTML (começados por `<`, ficam iguais); no texto `**…**`, `*…*`/`_…_`, `[…](…)` (externos com `target="_blank" rel="noopener"`) e HTML. Os blocos do primeiro nível levam `.reveal`. O parser YAML aceita blocos `|`/`|-` (linhas mais indentadas que a chave, sem comentários) para isto. Documentado no README.
- **Vídeos:** o build substitui `<!-- @videos -->` (secção `#videos` do `index.html`) pelo `<div class="video-grid reveal">` com um `a.video-thumb` (`data-youtube` = ID, miniatura de `i.ytimg.com`) por cada `youtube_1`/`youtube_2` do `section_media`; o ID é tirado do link (`watch?v=`, `youtu.be/`, `embed/`, `shorts/`, `live/`; outro formato dá erro). Um link vazio não é colocado (sem nenhum, o `<div>` também não; só com um, leva `.video-grid--single`, centrado e maior). O vídeo em destaque (secção cinzenta do `index.html`) vem de `section_single_video`: o build substitui `<!-- @video-destaque -->` pelo `.embed#live-video` (`data-youtube` do `youtube`, obrigatório; `data-title`, barra e rótulos com o `title_<língua>`) e pelo `.feature-text` com o título (`h3`) e o `text_<língua>` (um `<p>` por parágrafo, texto simples); título ou texto vazio não é colocado. Rótulos (`aria-label`/`alt`) na constante `ROTULOS`.
- **Fotos:** o build substitui `<!-- @fotos -->` (dentro do `div#music` do `index.html`) pelas `fotos` do `section_media`, sem limite: as duas primeiras no `<div class="covers-big reveal">` (destaque) e as restantes no `<div class="covers-grid reveal">`; cada uma é `<a href="images/…"><img … alt=""></a>` (o link abre a lightbox do `main.js`). Ficheiro inexistente dá erro; um contentor sem fotos não é colocado.
- **Agenda:** os concertos vêm de `section_agenda.gigs` do `home.yaml`; só contam os que têm `isEnabled: true`. Cada concerto precisa de `id`, `data` (`'AAAAMMDD'`), `name` e `location`; os campos de texto aceitam versão inglesa com sufixo `_en` (ex.: `name_en`). Os textos fixos gerados pelo build (botões, títulos) estão na constante `ROTULOS`. Um concerto sem `imagem_h` usa `section_agenda.default_images.hero` e um sem `imagem_v_4x5` usa `default_images.hero_v` (também na imagem de partilha).
  - **Lista:** o build substitui `<!-- @agenda -->` (dentro da `<ul class="tour-list">` do `index.html`) por um `<li>` por concerto. Só entram os de hoje em diante (à data do build), por ordem cronológica. O nome leva à página do concerto; o botão leva ao `ticketsLink` ("Bilhetes") ou, se não houver, à página do concerto ("Informações"). Cada `<li>` tem `data-date` (`AAAA-MM-DD`), e o `main.js` tira os que entretanto passaram (à data do visitante).
  - **Página do concerto:** `evento-<slug>.html` em cada língua (slug do `id`: minúsculas, sem acentos, hífenes; dois iguais dão erro), também para concertos passados. Vem de `src/modelos/evento.html`: `[[titulo]]` leva o `name`, `[[descricao]]` um resumo (data por extenso, hora, local e o início do `info`, até `RESUMO_MAX` caracteres) e `<!-- @evento -->` o conteúdo. Tem hero com `imagem_h` e `imagem_v_4x5` (`.hero-h`/`.hero-v`, a vertical só em ecrãs na vertical), ou só a que existir. Mostra título, data, hora, local, `info`, botão de bilhetes e, em **Local**, morada (com link para o `mapsUrl`), site, telefone e email. **Um campo vazio não é colocado**, nem o título de uma secção que fique vazia.
  - **Partilha (OG):** o header tem `og:title`/`og:description` (do `titulo`/`descricao`) e `<!-- @og -->` (`og:url`, `og:locale`). Num concerto com `imagem_v_4x5`, o build gera `dist/images/og/<slug>.jpg` (JPG 1440×1800, cortado ao centro, sem nada por cima; cache em `.cache/images/og/`; medidas e qualidade na constante `OG`) e acrescenta `og:image` (URL absoluto, com `SITE_URL`) e `twitter:card`. As outras páginas usam a `default_share_image` do `site.yaml`, convertida da mesma forma para `dist/images/og/_default.jpg`.
- **Línguas:** cada página de `src/` dá `dist/pagina.html` (pt) e `dist/en/pagina.html` (en). O texto traduzível escreve-se `{{#lang pt}}A nossa história{{/lang}}{{#lang en}}Our story{{/lang}}` (em páginas, partials e atributos, incluindo os do `<!-- @partial header … -->`); o build fica só com o bloco da língua da página e, se um bloco de outra língua ocupar linhas inteiras, tira essas linhas. Blocos não se aninham; língua desconhecida ou bloco sem par dão erro. Nas páginas em `en/`, os caminhos relativos para recursos (`css/`, `js/`, `images/`…) levam `../` automaticamente; os links para `.html` ficam iguais. `<!-- @idioma -->` (menu e footer) dá o link para a mesma página na outra língua (com bandeira `flag-pt.svg`/`flag-uk.svg`) e `<!-- @hreflang -->` (no `<head>`) os `<link rel="alternate" hreflang>`. Textos criados pelo `main.js` usam `t(pt, en)`, conforme o `<html lang>`. Os CTAs do hero usam `pt`/`en` do `home.yaml`.
- **Cookies / Google Analytics:** o build substitui `<!-- @analytics -->` (no `<head>` do `header.html`) por `<meta name="ga-id" content="…">` com o `google_analytics_id` do `site.yaml` (tem de ser `G-` + letras/dígitos; vazio tira a linha: sem GA nem aviso). O `main.js` lê essa `<meta>` e mostra o aviso de cookies (`.cookies`, criado pelo JS com `t()`, botões Recusar/Aceitar, link para `politica-cookies.html`); o GA (`gtag.js` de `www.googletagmanager.com`) **só é carregado depois de aceitar**. A escolha fica no `localStorage` (`cookies-consentimento` = `aceite`/`recusado`); recusar depois de aceitar desliga o GA (`ga-disable-<id>`) e apaga os cookies `_ga*`. Os elementos `[data-cookies]` (botão "Preferências de cookies" no footer e na política de cookies) vêm com `hidden` e o JS mostra-os quando há GA; ao clicar, reabrem o aviso. As páginas legais usam `<article class="post legal">`; ao mudar o que o site recolhe (newsletter real, novos serviços externos), atualizar o texto delas e a data "Última atualização".
- **Paletas:** `paletas` do `paletas.yaml` é uma lista de IDs do colorhunt.co (24 dígitos hex = 4 cores) ou links deles. Para cada uma, `cssPaleta()` no `build.js` gera `dist/palettes/<id>.css`, que redefine as variáveis de `:root` (e algumas regras de cor de texto) por cima do `style.css`: as 4 cores vão para `--rust`/`--gold`/`--grey-light`/`--aqua` pela permutação com mais pontos (contraste do texto de cada secção, `--gold` sobre o escuro, secções seguidas distintas; mínimos na constante `PALETA`), `--black` é a mais escura escurecida e `--ticket-red` vem da paleta, escurecida se preciso. O build preenche `/* @paletas */` em `js/palette.js` com os IDs (e o hash de cada CSS) e escreve o URL de cada uma. O `palette.js` (no `<head>`, depois do `style.css`) só carrega o CSS com `?palete_id=<id>` conhecido e acrescenta o parâmetro aos links `.html`. **O tema original (`style.css`) não se altera por causa das paletas.**
- **Movimento reduzido:** respeitar `prefers-reduced-motion` — no CSS há um bloco global que desliga animações/transições, e o JS verifica `reduceMotion` antes de animar.
- **Acessibilidade:** `aria-label` nos links só com ícone, `alt=""` em imagens decorativas, `aria-expanded`/`aria-hidden` atualizados pelo JS no menu.

## Imagens

Pôr em `src/images/` só os originais (PNG/JPG). O build gera `.avif` e `.webp` ao lado de cada um em `dist/images/` (com `sharp`; qualidade em `FORMATOS` no `build.js`; cache em `.cache/images/`, refeita quando o original muda) e envolve cada `<img src="images/…">` das páginas num `<picture>` com `<source>` AVIF → WebP, ficando o `<img>` original como fallback. No HTML de `src/` escrever só o `<img>` normal. Os favicons (`images/favicon-32.png` e `images/apple-touch-icon.png`, ligados no `header.html`) são gerados pelo build a partir do `logo.jpg` (constante `FAVICON`). O CSS tem `picture { display: contents; }` para o `<picture>` não afetar o layout, mas seletores estruturais (`:nth-of-type`, `>`, `:first-child`) sobre imagens locais têm de contar com o `<picture>` (ex.: `.covers-big a:first-child img`).

## Caminhos

Como o site é servido num subcaminho do GitHub Pages, **todos os caminhos de recursos são relativos** (`css/style.css`, `images/hero01.png`), nunca começam por `/`.

## Segurança / CSP

- **Sem scripts nem estilos inline** (nem atributos `style="..."` no HTML); CSS e JS vão em ficheiros. Alterar estilos a partir do JS via `element.style` é permitido.
- Domínios externos em uso: Google Fonts (`fonts.googleapis.com`, `fonts.gstatic.com`), Font Awesome via `cdnjs.cloudflare.com` e imagens de `placehold.co` e `i.ytimg.com` (miniaturas do YouTube); o leitor do SoundCloud (iframe na secção Música do `index.html`) vem de `w.soundcloud.com`; o Google Analytics vem de `www.googletagmanager.com` (script) e envia dados para `*.google-analytics.com`, `*.analytics.google.com` e `*.googletagmanager.com`; o leitor do YouTube vem de `www.youtube-nocookie.com` (iframe criado pelo JS só ao clicar numa `.video-thumb[data-youtube]` ou `.embed[data-youtube]`; links com `data-play="<id do embed>"` também o arrancam).
- A CSP em `netlify.toml` permite `'self'` mais estes domínios (cada um só na diretiva de que precisa: `img-src`, `script-src`, `connect-src`, `style-src`, `font-src`, `frame-src`). No GitHub Pages não tem efeito. Novos domínios externos têm de ser acrescentados lá; quando os placeholders forem substituídos, retirar `placehold.co`.
